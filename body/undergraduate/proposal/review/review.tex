\section{背景介绍}

RISC-V 处理器凭借其低成本与生态优势，在物联网、嵌入式以及高性能计算领域获得了广泛的应用。
然而，随着 RISC-V 处理器的应用不断拓宽，针对处理器底层硬件的安全威胁也日益凸显。
在这些安全威胁中，侧信道攻击能够隐蔽地利用处理器执行过程中的状态残留，跨越特权边界窃取系统机密信息，造成了了极大的安全隐患。
硬件级缺陷在芯片流片后难以修复，所以必须在处理器设计阶段将其消除。
形式化验证作为一种静态分析技术，能够对硬件设计的全局状态空间进行探索，完备地捕捉深层隐蔽缺陷。
因此，在芯片设计阶段引入形式化验证技术进行侧信道漏洞检测，已成为保证处理器安全的关键手段。
基于此研究背景，本章将从 RISC-V 处理器、侧信道漏洞与形式化验证三个方面展开综述。


\subsection{RISC-V 处理器}

RISC-V 是一种开源的精简指令集架构（Instruction Set Architecture，ISA），目前在学术界和工业界得到了广泛的应用。
该架构支持基础的整数指令集与若干可选的标准扩展指令集，如乘除法扩展、原子操作扩展、浮点扩展等。
RISC-V 处理器的开发者根据性能、安全等需求，设计不同复杂度的硬件实现，即微架构。
以 Ibex\cite{ibex} 为代表的轻量级处理器通常采用简单的单发射、顺序执行以及极短的流水线设计；
以 CVA6\cite{zaruba2019cost} 为代表的处理器通常采用多流水线、乱序发射技术；
以 BOOM\cite{zhaosonicboom} 为代表的复杂处理器通常采用超标量、乱序执行、深度流水线及多级分支预测等激进的性能优化技术。

\begin{figure}
    \centering

    \caption{CVA6 处理器微架构图}
    \label{fig:cva6}
\end{figure}

为了不断提高的计算性能，现代 RISC-V 处理器在微架构层面引入了大量复杂的优化部件。
以图 \ref{fig:cva6} 所示的 CVA6 处理器微架构为例，其内部集成了多种典型的性能加速机制：
分支历史表（Branch History Table，BHT）根据历史分支指令的跳转结果做出分支预测，减少分支预测错误的惩罚；
返回地址栈（Return Address Stack，RAS）记录函数调用链的返回地址，加速函数调用的返回过程；
缓存（Cache）保存频繁读取的内存数据，减少内存访问次数；
计分板（Scoreboard）进行指令的乱序发射，将计算结果进行前递，降低了指令之间的数据冲突。
值得注意的是，这些复杂的微架构状态单元，在提升处理器性能的同时，也打破了严格的物理隔离边界，为隐蔽的侧信道漏洞埋下了安全隐患。


\subsection{侧信道漏洞}

侧信道漏洞指处理器在运行过程中的物理泄露或微架构状态泄露，进而导致了计算机系统中的机密信息泄露。
本文主要关注基于处理器微架构状态差异的侧信道漏洞。
现代处理器微架构为了追求高性能，广泛使用 Cache、BHT 等微架构部件来提高指令执行效率。
例如，缓存命中（Cache Hit）可以节约几十个时钟周期的访存时间开销。
所以即使执行同一条指令，也有可能因为微架构状态的不同，从而使得指令执行的时间出现差异。
程序中不同机密数据的值参与计算会在微架构上留下不同的状态。
所以攻击者可以根据指令执行行为的差异，推测出微架构的状态，从而推测出机密数据的值。

侧信道漏洞可以分为微架构状态编码和微架构状态解码两个阶段。
在微架构编码阶段，受害者会读取机密数据进行运算，这些运算会对微架构状态产生改变；
% 或者是攻击者通过架构不可见的方式读取机密数据，并将机密数据固定在微架构状态中。
在微架构解码阶段，攻击者通过微架构解码原语\cite{184415}，将微架构状态恢复为架构可见的值。

侧信道漏洞可以分为瞬态执行漏洞、常量时间执行违例漏洞和计时器无关漏洞三种。

1. 瞬态执行漏洞利用现代处理器的推测执行或异常延迟处理，投机执行某些本不会被执行的代码。
攻击者通过训练分支预测器\cite{8835233}、毒害返回地址栈\cite{10.1145/3243734.3243761}、人为触发异常\cite{10.1145/3357033}、
制造端口争用\cite{10.1145/3319535.3363194}或微架构采样\cite{10.5555/3277203.3277277}来打开瞬态执行窗口。
在这个瞬态执行窗口中，处理器会根据攻击者的意图执行某些代码片段。
这些代码的执行结果虽然会被撤销，但是却将某些机密信息编码到了微架构中。
这些编码了机密信息的微架构就可以作为侧信道，解码机密信息。

2. 常量时间执行违例漏洞是一种利用指令执行时序差异泄露机密信息的侧信道漏洞。
现代处理器为了效率最大化，会在硬件电路上对整数除法、浮点运算等运算单元进行时序优化\cite{10.5555/3698900.3699201}\cite{10.5555/3620237.3620638}。
导致这些指令执行所需的时钟周期（Clock Cycles）依赖于输入操作数的具体数值。
如果在处理机密信息时使用了非恒定时间执行的指令，攻击者便可以通过测量指令执行时间，并将其映射为机密数据的值，
从而实现信息窃取。

3. 计时器无关漏洞\cite{10.1145/3719027.3744833}\cite{291182}不依赖指令执行时间差异来解码微架构中的状态信息。
在传统的侧信道攻击中，攻击者通常需要使用高精度的计时器来测量微架构状态的差异。
%现代的处理器为了防御侧信道漏洞攻击，很多不再提供高精度的计时器。
但是现代处理器为了修复侧信道漏洞，往往精致用户态程序使用高精度计时器。
而计时器无关的侧信道攻击在微架构解码阶段无需使用计时器，而是利用一种原子指令原语\cite{10.1145/3719027.3744833}\cite{291182}。
这种原语可以将缓存状态反映到架构寄存器上，提供了一种新的微架构状态解码方式。


\subsection{形式化验证}
形式化验证是一种基于严格数学基础的系统正确性分析与验证技术。
其通过静态的符号化穷举的方式遍历待验证对象的全局状态空间，能够以数学上的完备性覆盖所有可能的执行路径与输入组合。
形式化验证被应用到处理器设计上，用于验证处理器是否存在侧信道漏洞\cite{10.1145/3658644.3690344}\cite{10.1145/3613424.3614254}。
一般来说，针对处理器的形式化验证分为以下三步进行：

1. 验证对象建模。验证对象建模是形式化验证的第一步，也是决定漏洞检测精度与求解效率的核心基础。
形式化验证首先需要将待测硬件转换为一个严格的逻辑系统。
这个逻辑系统既可以采用高抽象层级的数学状态转移模型来描述，也可以直接使用底层硬件的寄存器传输级（RTL）代码来构建。
以 RTL 代码为例，在确定了验证的顶层模块后，该模块的输入信号会被形式化验证引擎抽象为无约束的符号值。
代表其在任意时刻可以接受任意合法的输入组合。这种符号化抽象赋予了验证引擎在数学上穷尽系统全局状态空间的能力。

2. 安全属性约束。形式化验证的核心是通过数学方法验证一个系统是否满足某些属性，安全属性直接决定检测出的漏洞类型与质量。
验证者需要从抽象的安全规范中提取安全原则，将其形式化为一组能够被求解引擎识别的安全属性。
具体来说，安全属性是待验证对象在时序或者逻辑上应该满足的某些不变量。
在工程实践中，这些安全规范一般使用 SystemVerilog Assertions 进行编写。
语法体系自底向上划分为布尔表达式、序列与属性三个层次，能够对复杂的微架构时序动作进行建模，从而捕获的处理器侧信道安全违例。

3. 形式化引擎求解。
形式化引擎首先将处理器RTL代码抽象为数学状态转换系统，同时将安全属性转化为时序逻辑命题。
形式化引擎随后在全局状态空间内穷举可能的输入序列。
% 然而，这一穷举求解动作的计算代价极其高昂。
% 面对现代处理器庞大的微架构状态，形式化引擎需要解析的状态变量会呈指数级激增，引发状态空间爆炸。
% 这成为严重制约现有处理器漏洞检测框架验证深度的最大技术瓶颈。
% 4. 验证结果分析。形式化验证具有完备性。
如果某个侧信道安全属性被引擎成功证明，则意味着在数学意义上排除了该安全属性被破坏的任何可能性。
反之，如果某个安全属性被证伪，形式化验证引擎会给出一个周期级精确的反例。
同时，也有可能因为硬件设计规模过大导致状态爆炸求解超时。



\section{国内外研究现状}

处理器侧信道漏洞形式化检测是处理器的形式化验证的一种应用场景。
在上述基本概念基础上，现有研究主要围绕验证对象边界、安全属性设计与状态同步机制三条主线展开。
% 流程与传统处理器的形式化验证相似。
% 本章从验证对象的边界，待验证的安全属性与同步状态的定义三方面介绍针对处理器侧信道漏洞的形式化验证。

\subsection{研究方向及进展}

\subsubsection{验证对象的边界}
早期的形式化验证工作通常采用高抽象层级的纯数学模型，以完全规避底层硬件巨大的状态空间。
InSpectre\cite{10.1145/3372297.3417246}，Hardware-Software Contracts\cite{9519500} 和 CheckMate\cite{8574598} 为了规避底层硬件巨大的状态空间，
选择不以任何RTL代码作为求解顶层，而是构建一个包含投机执行特征的数学状态机模型。
这种抽象能够从更高抽象层级快速证明或证伪特定的投机执行机制。
这类抽象模型由于脱离了具体的硬件实现，无法发现因特定总线竞争、有限状态机错误等底层实现缺陷导致的侧信道漏洞。

为了弥补抽象模型在细节上的缺失，部分验证框架直接使用 RTL 代码作为验证对象，但往往需要借助黑盒化或模块化策略来降低求解复杂度。 
AutoCC\cite{10.1145/3613424.3614254} 将验证对象转移到真实的RTL代码上。
该框架的顶层边界可以是单独的如 AES 加速器的硬件加速器，或者是经过黑盒化处理的简单处理器核心。
当以处理器核心为顶层时，为了让求解器能在合理时间内得出结果，AutoCC 建议将内部状态过于复杂的子模块作为黑盒移出验证边界。
但是这种方法难以找到模块间复杂交互的漏洞，在一定程度上牺牲了状态探索的完整性。

最新的研究工作致力于打破内部模块边界，尝试将验证范围全面扩展至完整的处理器核心。
$\mu$CFI\cite{10.1145/3658644.3690344} 将其验证顶层设定为顺序执行的处理器核心，如 Ibex，PicoRV32 等，整个CPU的所有流水线阶段均在其求解边界之内。
$\mu$CFI 成功发现了 Ibex 处理器内部乘法器与异常处理模块之间的侧信道。
Contract Shadow Logic\cite{10.1145/3669940.3707243} 将边界进一步拓展到了复杂的乱序执行处理器核心。
该工作的验证顶层包含了两份完整的乱序核心RTL代码以及辅助验证的影子逻辑。
Contract Shadow Logic 使用影子逻辑过滤了部分求解需求，
实现了对状态空间一定的裁剪，
从而缓解了形式化求解引擎难以对复杂乱序处理器进行求解的问题。



\subsubsection{待验证的安全属性}
\label{sec:property}
针对微架构侧信道，研究者们定义了各类安全属性。
首先，研究者提出了基于参考模型的安全契约。
InSpectre\cite{10.1145/3372297.3417246} 提出了条件非干扰性。
即证明处理器在引入乱序和预测执行等优化后，不会比顺序执行的参考模型泄露更多的信息。
类似地，Hardware-Software Contracts\cite{9519500} 中定义了推测非干扰性。
要求程序在顺序执行时不可区分的状态，在投机执行下也必须对攻击者不可区分。形式化地表示为：
$$\forall P,\ M_{pub},\ M_{sec},\ M'_{sec}$$
$$\mathbf{if}\ O_{ISA}(P,\ M_{pub},\ M_{sec})\ =\ O_{ISA}(P,\ M_{pub},\ M'_{sec})$$
$$\mathbf{then}\ O_{\mu Arch}(P,\ M_{pub},\ M_{sec})\ =\ O_{\mu Arch}(P,\ M_{pub}, M'_{sec})$$
其中，$P$ 表示一段输入程序；
$M_{sec}$ 指内存空间中储存机密信息的部分，$M_{pub}$ 则是内存空间中除去 $M_{sec}$ 的其他部分；
$O_{ISA}$ 和 $O_{\mu Arch}$ 分别指从架构层和微架构层的观察结果。 
Hardware-Software Contracts\cite{9519500} 的安全属性从软硬件层面解释为：
对于相同程序和公开输入，若两组不同机密输入在 ISA 层不可区分，则在微架构层也不应出现可被攻击者区分的差异。
即，如果软件满足特定的沙盒约束或恒定时间编程约束，则硬件承诺在此契约下不发生泄露。

随着验证维度的下沉，后续工作致力于将这一高度抽象的数学契约具象化为可执行的底层检测规则。
Contract Shadow Logic\cite{10.1145/3669940.3707243} 直接将该安全属性转化为 RTL 级别的断言进行求解。
AutoCC\cite{10.1145/3613424.3614254} 使用了该安全属性的变体，观察微架构的差异能否引起架构的差异。

除基于可观测差异的微架构安全属性外，也有工作从信息流角度重构侧信道安全问题。
$\mu$CFI\cite{10.1145/3658644.3690344} 不再局限于传统的计时侧信道，而是定义一种信息流安全属性。
处理器在时钟周期级别的 PC 只能被 ISA 明确允许的指令操作数影响。
该属性将时序侧信道问题转化为了针对 PC 的污点追踪断言，统一了微架构侧的恒定时间执行与控制流劫持漏洞检测。


\subsubsection{同步状态的定义}

在高层抽象模型中，早期的研究工作主要依赖严格的数学等价关系来界定抽象的执行步同步。
Hardware-Software Contracts\cite{9519500} 和 InSpectre\cite{10.1145/3372297.3417246} 通过不可区分性等数学关系来静态定义同步状态。
它们在每个求值步骤中，约束要求两个实例保证内存一致性。
即确保无论是顺序执行模型还是乱序执行模型，写内存顺序在两者之间是相同的，以此在最高维度上保证了架构状态的一致性。

随着验证对象向真实硬件细节发展，同步状态的定义逐渐从抽象的数学关系具体化为粗粒度的硬件刷新事件。
在 AutoCC\cite{10.1145/3613424.3614254} 中，同步状态被明确定义为硬件冲刷。
工具强制两个实例在受害者进程结束、刷新机制执行完毕后达成状态同步，即拥有相同的架构状态。
随后，AutoCC 在给定的稳定周期后启动间谍进程，比较两者的微架构状态输出是否产生分歧。
然而这种硬件冲刷机制需要直接改变微架构的状态，可能导致假阳性漏洞的发生。

面对现代的乱序处理器，粗粒度同步难以应对由微架构事件引发的时序错位，最新的研究引入了细粒度的动态时序同步。
Contract Shadow Logic\cite{10.1145/3669940.3707243} 尝试通过引入两阶段影子逻辑解决这一问题。
当两个实例的微架构轨迹发生分化时，系统进入第二阶段，此时影子逻辑通过暂停较快实例的时钟，强制两个实例在指令提交当拍阶段实现周期对齐。
这表明同步机制已从静态数学等价逐步演进到面向真实乱序硬件的动态轨迹对齐。

\subsection{处理器侧信道漏洞形式化检测存在的问题}
% 尽管现有的工作在理论和工程上逐渐完善，但是由于处理器设计日益的复杂性与侧信道漏洞的丰富性，一个侧信道漏洞的根源，触发链越来越复杂。
% 这使得现有的处理器侧信道漏洞检测框架依然存在不足。
尽管现有的处理器侧信道形式化检测技术在理论与工程上逐步完善，但面对现代处理器的微架构复杂度以及新型攻击手段，现有框架逐渐暴露出明显的局限性。
具体而言，随着乱序执行等技术的引入，侧信道漏洞的成因更加隐蔽，其触发链条依赖复杂的微架构状态。
这种由硬件状态爆炸与漏洞形态多样化带来的双重挑战，使得现有的形式化检测框架在建模精度、安全属性完备性以及求解效率上依然存在以下瓶颈：


\subsubsection{验证对象建模与真实硬件存在语义偏差}
现有的处理器侧信道漏洞检测工作只关注核内部件的交互，却忽略了在真实硬件上，处理器核心同样需要频繁与总线、外设进行交互。
尽管最新的研究工作\cite{10.1145/3669940.3707243}\cite{10.1145/3658644.3690344}成功将形式化验证的边界扩展至完整的处理器核心，但这种将验证边界截断于核心接口的策略，可能导致假阳性问题。
形式化求解为了最大化状态空间的探索覆盖率，会将位于验证边界上的输入信号视为完全无约束的符号变量。
然而，在真实的片上系统（SoC）中，处理器核心与内存的交互受到极其严格的时序与总线协议，如AXI总线协议的约束。
为了触发安全属性违例，形式化求解器可能找出违反总线协议的非法输入序列。
$\mu$CFI\cite{10.1145/3658644.3690344} 提出的一个漏洞要求总线上的 $\texttt{data\_err}$ 和 $\texttt{data\_rvalid}$ 信号同时为 1，但是这违反了总线协议的要求，攻击者使用纯软件方案无法触发。
同时，在传统的处理器形式化建模中，研究人员通常只关注核心内部，而忽略了处理器核心与外设之间的交互。
然而，在真实的 SoC 中，一些通用的外设本质上也可被视为整体微架构的延伸。
它们同样具备编码和残留机密信息的能力，从而可能被攻击者利用，成为打破核心隔离边界的新型侧信道泄漏源。

\subsubsection{侧信道安全属性定义存在局限}
随着侧信道攻击手段的演进，现有的安全属性无法捕获微架构向架构层泄漏的通道。
传统的处理器侧信道漏洞检测框架使用的安全属性高度依赖于显式的微架构观测通道，通常将安全性定义为机密数据不应影响处理器的执行时间或访存行为。
然而，计时器无关\cite{10.1145/3719027.3744833}\cite{10.1145/3719027.3765061}\cite{291182} 攻击完全摒弃了对高精度计时器的依赖。
它们巧妙地将微架构的隐藏状态，如指令缓存行是否被受害者逐出，直接转化为架构层面可见的执行结果。形式化表示为：
$$O_{ISA}(P,\ M_{pub},\ M_{sec})\ \neq\ O_{ISA}(P,\ M_{pub},\ M'_{sec})$$
正如第\ref{sec:property}节所阐释的，只有两条轨迹架构行为一致时，才会检查微架构是否满足约束。
如果两条指令架构层的行为不一致的话则无需检查。
对于计时器无关攻击，泄漏恰恰可能表现为架构层行为的差异。
由于现有的安全属性并未将微架构状态直接篡改架构级控制流或数据流作为一种泄露途径进行建模，计时器无关攻击可以绕过传统安全属性的检测。

\subsubsection{双实例状态同步导致状态爆炸}
现有框架中计算密集的处理器多实例状态同步机制，是导致侧信道形式化检测陷入状态空间爆炸的核心瓶颈。
在现有的大多数处理器侧信道与瞬态执行漏洞形式化验证中，需要同时追踪并比较两条具有不同机密数据输入的执行轨迹。
为了对比这两条轨迹在微架构层面的观测差异，现有的验证框架严重依赖于复杂的状态同步或轨迹对齐机制。
然而，在现代处理器中，由于缓存未命中、分支预测差异或指令延迟的不同，两条轨迹在时钟周期上可能产生偏移。
为了对齐这些异步状态，现有的工作通常采取两种策略：
在RTL层引入辅助影子逻辑和对齐约束\cite{10.1145/3669940.3707243}，这加剧了约束求解时的状态空间爆炸；
或是要求求解器从初始复位状态开始，符号化地执行前缀指令序列\cite{10.1145/3613424.3614254}，试图让两条轨迹在某个深层状态会和并同步，
这种依赖长路径推导来实现状态同步的范式，计算开销极其高昂。


\section{研究展望}
首先，现有的处理器侧信道漏洞形式化检测工作由于对测试对象的建模不准确，导致找出的安全属性反例可能违反了真实世界的总线约束。
同时，对 SoC 上的外部设备的忽略可能导致威胁模型不够真实完整。
为了解决这些问题，处理器侧信道形式化检测框架可以考虑将总线、内存以及某些通用外设纳入测试对象的建模中。
并且将内存中储存指令与数据的地址空间约束为抽象值。
这样可以保证处理器顶层的输入合法，也可以生成可以直接运行的测试样例；
同时也合理地拓展了威胁模型，关注了真实世界硬件的行为。

其次，现有的处理器侧信道漏洞安全属性完备性不足。
现有的安全属性关注显式的微架构观测通道，例如指令执行时间，访存行为等。
但是新的侧信道攻击微架构解码手段层出不穷。
当微架构解码手段不依赖传统的观测通道时，传统的处理器侧信道漏洞安全属性就会失效。
这要求研究人员发展出更通用的针对处理器侧信道漏洞的安全属性。

最后，现有的框架在处理双实例状态同步时，面临着效率与有效性的双重瓶颈。
一方面，复杂的延迟同步逻辑会使求解逻辑变得复杂，从而导致的求解难度增大；
另一方面，从初始状态带着符号求解又难以发现深层次的漏洞，若是强制约束求解步长又大大降低了漏洞发现效率。
这种两难困境大幅拉低了侧信道漏洞的挖掘效率。
总的来说，未来的工作需探索一种状态压缩机制，以剥离冗长的前缀执行，直接将求解器引导至深层同步状态。
